# 十二橙器后端

前后端已接通：Nuxt `/api` 代理 → NestJS → MySQL。运行与部署见 [deployment.md](deployment.md)，数据库实际结构以 `apps/api/src/schema.ts` 为准。

## 届次和规则

- 第一届 `/ranking` 保留原只读书单，不补造选票。
- 第二届起默认筹备中，四个日期为空，前台显示“时间待公布”。每人提名 3 部、投票 3 张、计划入选 12 部为可编辑初值，管理员在开放前确认。
- 状态顺序 `draft → nomination → voting → results → archived`，由管理员推进；有配置日期时提交还必须处于对应窗口。
- 开放提名后锁定名额与计分规则，公布后仅可修改活动名称。配置和阶段推进携带 version，避免旧页面覆盖新设置。
- 提名默认 pending，管理员通过或填写原因退回；成员可撤回本人提名。退回和撤回不占有效名额。同一作品规范化后合并候选，保留各位推荐语。
- 进入投票前必须处理所有待审核提名，且至少一部候选通过。进入投票后不能再修改提名。
- 每人每轮一张有效选票，真爱与喜爱作品互斥，推荐词只给已投作品额外加分；修改整张替换。服务端事务和唯一约束防止重复计票，version 和 round 阻止旧标签页覆盖。
- 撤回选票保留递增的版本记录，空选票不计入投票人数或结果。再次提交仍须携带最新版本，避免撤回、重投后的版本重复问题。
- 提名阶段公开待审核与已通过的作品和提名人，同一用户不能重复提名同一作品，多位用户可提名同一作品，合并为一个候选。退回及撤回记录仅本人和管理员可见。
- 投票期间公开所有候选的实时分数（含零分）及推荐词作者，前台每 15 秒刷新；他人的账号与选票、审核备注和审计日志仅管理员可见。刷新分数保留尚未提交的选票。
- 公布时事务生成固定结果快照，并锁定写入。按本届计分规则得到的总分降序，同分并列并跳号；仅得票大于零且排名不超入选名额的作品入选，边界同票可能使数量超额。

## 角色

| 能力 | 普通成员 | 管理员 | 超级管理员 |
| --- | --- | --- | --- |
| 提名和投票、撤回本人记录 | ✓ | ✓ | ✓ |
| 配置当届活动、审核、推进到公布 | — | ✓ | ✓ |
| 创建届次、归档 | — | ✓ | ✓ |
| 查看账号、启停账号及分配角色 | — | — | ✓ |

角色来自数据库和有效登录会话。活动写请求在事务内重新校验账号状态及权限；系统始终保留至少一名有效超级管理员，变更角色会撤销受影响账号的会话。

## 数据表

| 表 | 用途 |
| --- | --- |
| award_campaigns | 届次唯一、活动配置 JSON、version |
| award_candidates | 规范化标题在当届唯一，关联作品资料与封面 |
| award_nominations | 成员、候选、审核状态、推荐语和反馈 |
| award_ballots | (campaign_id, user_id) 唯一；选票 JSON 与递增版本 |
| award_results | 每届唯一的公布结果快照及有效选票数 |
| system_locks | 活动与权限变更的事务串行化入口 |
| audit_logs | 服务端追加的配置、审核、参与和权限操作记录 |

同一活动的提名、审核、选票与推进操作先锁活动行再校验并写入，保证并发配额与关票时的一致性。持久化时间使用 UTC，页面按 UTC+8 展示。

## 实际接口

| 接口 | 用途 |
| --- | --- |
| GET /api/award-campaigns | 届次列表 |
| GET /api/award-campaigns/:id | 根据会话权限返回公开、本人与管理所需数据 |
| POST /api/admin/award-campaigns | 管理员创建草稿 |
| PATCH /api/admin/award-campaigns/:id | 管理员保存配置，携带 version |
| POST /api/admin/award-campaigns/:id/transitions | 推进阶段，携带 phase 与 version |
| POST /api/award-campaigns/:id/nominations | 提名 title / studio / reason |
| PATCH /api/award-campaigns/:id/nominations/:nominationId | status=withdrawn / approved / rejected，退回必须附 note |
| PUT /api/award-campaigns/:id/ballot | candidateIds 与 version；candidateIds=null 撤回 |
| GET /api/admin/users | 管理员查看账号列表（含头像地址） |
| PATCH /api/admin/users/:id | 管理员修改账号状态；角色变更仅限超级管理员 |

写接口要求有效会话、同源请求与 CSRF 校验；提名与投票有独立限流。失败使用 401、403、404、409、422 或 429，客户端必须处理异常后刷新状态。

手动提名新作品时可上传封面（JPG、PNG、WebP，最大 5 MB），预览、更换或移除。先调用 `/api/uploads`，再将返回的图片编号作为可选 `coverAssetId` 提交到提名接口；图片必须属于当前账号且处于有效状态，不能与 `workId` 或 `subjectId` 混用。封面与新书库作品在提名事务内关联，配额、阶段或去重校验失败时不会留下新作品。已有作品复用书库封面，不能通过再次提名覆盖封面。封面保存在原书库 JSON 中，无需数据库迁移；部署时需同时更新前后端并重启 API。

评选规则在前端 `app/utils/awards.ts` 和类型中维护，通过 `scripts/sync-award-rules.mjs` 同步至 API；构建命令会自动执行同步。服务端规则和数据库事务是最终裁决依据，前端只负责交互提示。

## 自定义规则与活动删除

管理员在 `/admin/awards` 新建活动后，可修改名称、时间、提名名额、入选名额、投票规则。默认真爱票 1 张、每张 2 分；喜爱票 2 张、每张 1 分；每份推荐词额外加 2 分，最多 3 份。推荐词选填，每个本人投票的作品最多一份；取消该作品选票时也需移除对应推荐词。提名说明选填且不参与推荐词加分。

筹备阶段可以自定义真爱／喜爱票张数（各 0–10 张，合计至少 1 张）、各自分值和推荐词分值（0–100）、每人推荐词份数上限（不能超过可投作品数，0 表示关闭）。开放提名后，配额与计分规则锁定；投票时间内可改票和撤回，以最新提交为准。结果显示总分及真爱票、喜爱票、推荐词份数，公布后的快照保持不变。

新建和原筹备中活动采用加权规则；已开放的旧活动保留原规则，不能将旧选票直接按新分数重算。配置和选票均保存在原有 JSON 字段，不需要数据库迁移。前后端应一并更新，旧版前端不能提交加权选票，服务端会提示重新填写。

管理员删除活动需要输入完整活动名称并携带当前版本号。确认时前后端统一转换全角字符、忽略空格，其余文字必须匹配；界面显示待删除名称、匹配提示和删除失败原因。手机端输入框独占一行，取消与确认按钮分隔排列。旧后端缺少 DELETE 接口时提示更新并重启后端，不能仅更新前端。

逻辑删除后，公开列表和管理列表不再展示，详情和写入返回 404；保留参与记录、结果和审计记录，避免误删级联数据。届次编号不会复用，所有活动删除后仍可创建新一届。

活动前台刷新时先显示加载状态，再展示接口返回的实际届次；不在等待期间显示默认第二届。请求失败时保留明确提示与重试入口。

## 二次投票与后台数据

后台设置按提名、投票排列，投票候选只来自本届审核通过的提名，书库其他作品不进入选票。首轮有效得分作品不足 `winnerCount`（默认 12）时，接口拒绝直接公布；管理员在阶段推进中确认“开启二次投票”，调用 `POST /api/admin/award-campaigns/:id/runoff`，携带当前 `version`。服务端保存首轮快照，保留已得分作品和分数，只对其他正式提名作品开放补投。二次投票独立使用同一套票种与分值；旧页面提交 `round: 1` 会收到 409。二次投票起止时间会清空，可在后台重新配置。

首轮作品优先保留名额，补投作品按二轮得分竞争剩余名额，边界同分仍并列。二次投票结束后可公布实际结果；若提名总数不足或仍有零分作品，不虚构十二部结果，前后台均提示实际数量。二次投票限一轮，不支持重复开启。投票人数显示两轮有效选票份数合计，不是去重参与人数。

管理员“投票数据”页可查看全部轮次选票（含撤回记录）、账号、票种、推荐词、作品分数和完整操作日志。公开响应没有 `ballots`、`rounds`；推荐词仅附作者显示名和轮次。首轮历史存入原 `award_results` JSON，当前轮继续使用 `award_ballots`，不新增表、无需迁移；账号注销时也匿名处理首轮历史。部署应同时更新前后端并重启 API。

## 第二届QQ群提名临时同步

管理员在第二届的“提名审核”中选择“全部记录”，可对已有提名点击“同步提名人和日期”，填写QQ群提名人的昵称和实际提名时间。时间按北京时间 UTC+8 输入和显示，可早于网站开放提名的时间，不允许填写未来时间。同步后前台提名人及日期使用QQ群信息，并标注来源；后台继续显示原网站提交人和时间。此入口仅当届次 `edition === 2` 时显示，服务端同样检查届次，第三届及以后的正常提名、去重、名额和审核流程保持不变。

接口为 `PATCH /api/admin/award-campaigns/:id/qq-nominations/:nominationId`，字段为 `nominatorName`（1–64 字）、`nominatedAt`（含时区的 ISO 时间）、`revision`（从管理员活动详情中的 `qqSyncRevision` 获取）。校验管理员权限、同源请求、CSRF 和并发修改；其他管理员先修改或审核过该记录时，旧版本返回 409。每次修改保存旧、新姓名和时间以及操作人审计。

同步信息单独保存在提名 JSON 的 `qqSync` 中，不改动 `accountId`、`accountName`、`createdAt`、候选编号、审核状态、选票或计分。原始提交账号仍决定名额和同人去重。第二届进入投票、二次投票、结果公布或归档后，仍可修正展示信息；前台历史结果中的提名署名采用最新同步信息，保存的结果快照、分数与排名不重算。此功能不创建新提名，不自动通过审核，也不改变其他届次。无需新增数据库迁移，部署时更新前后端并重启 API。
