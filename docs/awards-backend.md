# 十二橙器后端

前后端已接通：Nuxt `/api` 代理 → NestJS → MySQL。运行与部署见 [deployment.md](deployment.md)，数据库实际结构以 `apps/api/src/schema.ts` 为准。

## 届次和规则

- 第一届 `/ranking` 保留原只读书单，不补造选票；前台届次选择器统一提供第一届与后续届次入口，历史书单不作为可编辑活动写入数据库。
- 第二届起默认筹备中，四个日期为空，前台显示“时间待公布”。每人提名 3 部、投票 3 张、计划入选 12 部为可编辑初值，管理员在开放前确认。
- 状态顺序 `draft → nomination → voting → results → archived`，由管理员推进；有配置日期时提交还必须处于对应窗口。
- 开放提名、开放投票、结果公布、归档、开启二次投票及每轮同票加赛时，向所有有效账号发送站内活动通知，链接指向对应届次。通知与阶段变更在同一事务提交，以活动、阶段及加赛轮次作为唯一事件键，失败或并发重试不会重复发送；通知可在后台通知管理中查看。
- 开放提名后锁定名额与计分规则，公布后仅可修改活动名称。配置和阶段推进携带 version，避免旧页面覆盖新设置。
- 提名默认 pending，管理员通过或填写原因退回；成员可撤回本人提名。退回和撤回不占有效名额。同一作品规范化后合并候选，保留各位推荐语。
- 进入投票前必须处理所有待审核提名，且至少一部候选通过。进入投票后不能再提交、撤回或审核提名；管理员仍可更正展示姓名、时间和提名词。
- 每人每轮一张有效选票，真爱与喜爱作品互斥，推荐词只给已投作品额外加分；修改整张替换。服务端事务和唯一约束防止重复计票，version 和 round 阻止旧标签页覆盖。
- 撤回选票保留递增的版本记录，空选票不计入投票人数或结果。再次提交仍须携带最新版本，避免撤回、重投后的版本重复问题。
- 提名阶段公开待审核与已通过的作品和提名人，普通成员和普通管理员不能重复提名同一作品，仍受当届个人数量上限限制；超级管理员可重复提名、可超出个人数量上限，用于补录多位提名人的记录。每条仍需独立审核，同一作品合并为一个候选。该例外不绕过提名阶段、时间窗口或接口限流。退回及撤回记录仅本人和管理员可见。
- 投票期间公开所有候选的实时分数（含零分）及推荐词作者，前台每 15 秒刷新；他人的账号与选票、审核备注和审计日志仅管理员可见。刷新分数保留尚未提交的选票。
- 公布时事务生成固定结果快照，并锁定写入。实时计分暂保留同票组；所有有效得分作品的名次必须通过加赛分出唯一位次后，才能公布或归档。仅得票大于零且最终排名不超入选名额的作品入选，入选边界不再因同票超额。

## 同票加赛

同票加赛由管理员调用 `POST /api/admin/award-campaigns/:id/tie-break`，携带当前 `version`。每组每人最多选择一部作品，每票计 1 票，可对部分组弃权；不使用真爱票、喜爱票或推荐词加分。每轮只重排当轮同票组，其他名次和原始得分保留；未分出的子组可继续加赛，轮次不限定为两轮。零票未入选作品不占最终名次，不单独加赛。

轮次、加赛名单由服务端生成，设置接口不能篡改。旧轮次、重复投票版本、组外作品或一组多选均拒绝；新一轮选票从空白开始，旧选票、署名推荐词、分数与审计记录全部保留。轮次和快照沿用现有 JSON 字段，无需新增数据表。已公布或归档的旧届次若仍有同票，也可通过该接口重新开放投票；原结果和历史参与记录先存档，加赛结束后重新公布、归档，并发送对应轮次的新通知。

| award_campaigns | 届次唯一、活动配置 JSON、version |
| award_candidates | 规范化标题在当届唯一，关联作品资料与封面 |

同一活动的提名、审核、选票与推进操作先锁活动行再校验并写入，保证并发配额与关票时的一致性。持久化时间使用 UTC，页面按 UTC+8 展示。

## 实际接口

| 接口 | 用途 |
| --- | --- |
| GET /api/award-campaigns | 届次列表 |
| GET /api/award-campaigns/:id | 根据会话权限返回公开、本人与管理所需数据 |
| POST /api/admin/award-campaigns | 管理员创建草稿 |
| PATCH /api/admin/award-campaigns/:id | 管理员保存配置，携带 version |
| POST /api/admin/award-campaigns/:id/transitions | 推进阶段，携带 phase 与 version |
| POST /api/award-campaigns/:id/nominations | 提名 title / studio / reason |
| PATCH /api/award-campaigns/:id/nominations/:nominationId | status=withdrawn / approved / rejected，退回必须附 note |
| PATCH /api/admin/award-campaigns/:id/nomination-details | 管理员批量编辑提名人、时间与提名词，携带每条 detailsRevision |
| PUT /api/award-campaigns/:id/ballot | candidateIds 与 version；candidateIds=null 撤回 |
| GET /api/admin/users | 管理员查看账号列表（含头像地址） |
| PATCH /api/admin/users/:id | 管理员修改账号状态；角色变更仅限超级管理员 |

写接口要求有效会话、同源请求与 CSRF 校验；提名与投票有独立限流。失败使用 401、403、404、409、422 或 429，客户端必须处理异常后刷新状态。

手动提名新作品时可上传封面（JPG、PNG、WebP，最大 5 MB），预览、更换或移除。先调用 `/api/uploads`，再将返回的图片编号作为可选 `coverAssetId` 提交到提名接口；图片必须属于当前账号且处于有效状态，不能与 `workId` 或 `subjectId` 混用。封面与新书库作品在提名事务内关联，配额、阶段或去重校验失败时不会留下新作品。已有作品复用书库封面，不能通过再次提名覆盖封面。封面保存在原书库 JSON 中，无需数据库迁移；部署时需同时更新前后端并重启 API。

评选规则在前端 `app/utils/awards.ts` 和类型中维护，通过 `scripts/sync-award-rules.mjs` 同步至 API；构建命令会自动执行同步。服务端规则和数据库事务是最终裁决依据，前端只负责交互提示。

## 自定义规则与活动删除

管理员在 `/admin/awards` 新建活动后，可修改名称、时间、提名名额、入选名额、投票规则。默认真爱票 1 张、每张 2 分；喜爱票 2 张、每张 1 分；每份推荐词额外加 2 分，最多 3 份。推荐词选填，每个本人投票的作品最多一份；取消该作品选票时也需移除对应推荐词。提名说明选填且不参与推荐词加分。

筹备阶段可以自定义真爱／喜爱票张数（各 0–10 张，合计至少 1 张）、各自分值和推荐词分值（0–100）、每人推荐词份数上限（不能超过可投作品数，0 表示关闭）。开放提名后，配额与计分规则锁定；投票时间内可改票和撤回，以最新提交为准。结果显示总分及真爱票、喜爱票、推荐词份数，公布后的快照保持不变。

新建和原筹备中活动采用加权规则；已开放的旧活动保留原规则，不能将旧选票直接按新分数重算。配置和选票均保存在原有 JSON 字段，不需要数据库迁移。前后端应一并更新，旧版前端不能提交加权选票，服务端会提示重新填写。

管理员删除活动需要输入完整活动名称并携带当前版本号。确认时前后端统一转换全角字符、忽略空格，其余文字必须匹配；界面显示待删除名称、匹配提示和删除失败原因。手机端输入框独占一行，取消与确认按钮分隔排列。旧后端缺少 DELETE 接口时提示更新并重启后端，不能仅更新前端。

逻辑删除后，公开列表和管理列表不再展示，详情和写入返回 404；保留参与记录、结果和审计记录，避免误删级联数据。届次编号不会复用，所有活动删除后仍可创建新一届。

活动前台刷新时先显示加载状态，再展示接口返回的实际届次；不在等待期间显示默认第二届。请求失败时保留明确提示与重试入口。

## 二次投票与后台数据

后台设置按提名、投票排列，投票候选只来自本届审核通过的提名，书库其他作品不进入选票。首轮有效得分作品不足 `winnerCount`（默认 12）时，接口拒绝直接公布；管理员在阶段推进中确认“开启二次投票”，调用 `POST /api/admin/award-campaigns/:id/runoff`，携带当前 `version`。服务端保存首轮快照，保留已得分作品和分数，只对其他正式提名作品开放补投。二次投票独立使用同一套票种与分值；旧页面提交 `round: 1` 会收到 409。二次投票起止时间会清空，可在后台重新配置。

首轮作品优先保留名额，补投作品按二轮得分竞争剩余名额，边界同分仍并列。二次投票结束后可公布实际结果；若提名总数不足或仍有零分作品，不虚构十二部结果，前后台均提示实际数量。二次投票限一轮，不支持重复开启。投票人数显示两轮有效选票份数合计，不是去重参与人数。

管理员“投票数据”页可查看全部轮次选票（含撤回记录）、账号、票种、推荐词、作品分数和完整操作日志。公开响应没有 `ballots`、`rounds`；推荐词仅附作者显示名和轮次。首轮历史存入原 `award_results` JSON，当前轮继续使用 `award_ballots`，不新增表、无需迁移；账号注销时也匿名处理首轮历史。部署应同时更新前后端并重启 API。

## 多条提名展示编辑

管理员在各届“提名审核”中点击“编辑本作提名”，可在同一窗口分别编辑同一作品下多条提名的提名人、实际时间、来源和提名词，并可增加或删除提名人，一次保存全部操作。删除先标记为“待删除”，保存前可撤销；取消窗口不写入。选择“全部记录”可查看已审核、已退回或已撤回记录。可编辑已有活动的全部届次，不再限定第二届。第一届原只读书单没有活动提名记录，仍保留原展示方式。

时间按北京时间 UTC+8 输入和显示，可早于网站开放提名的时间，不允许未来时间。姓名 1–64 字，提名来源选填、最多 80 字（例如“QQ群”“网站”“线下活动”），提名词选填、最多 600 字，可清空。旧 QQ 同步记录默认显示“QQ群”，网站原记录显示“网站”，后台新增默认显示“后台补录”。提名词属于提名说明，不改变投票时的推荐词加分。新窗口自动读取旧 QQ 同步信息，前台作品摘要、提名列表及历史结果使用最新展示信息。

接口为 PATCH /api/admin/award-campaigns/:id/nomination-details，请求体支持 entries: [{ id, nominatorName, nominatedAt, reason, source, revision }]、additions: [{ nominatorName, nominatedAt, reason, source }]、removals: [{ id, revision }]，新增时携带 candidateId。三种操作在同一事务提交，任一校验失败全部回滚；旧版仅带 entries 的请求仍兼容。revision 来自管理员活动详情中每条记录的 detailsRevision。服务端校验管理员权限、同源请求、CSRF、活动归属和版本；任意记录被其他管理员修改或审核时返回 409，整批不保存，窗口保留输入并提示刷新。每次成功修改追加审计记录。

更正信息单独保存在提名 JSON 的 displayOverride 中，原始 accountId、accountName、createdAt、reason、候选编号与审核状态保留。提名配额仍按实际提交账号计算。投票、二次投票、结果公布和归档后也能更正展示信息，前台读取最新署名与提名词，保存的结果快照、选票、分数和排名不重算。后台新增保存在原提名表，标记 adminAdded，不占操作人的个人提名配额。提名阶段新增为待审核；投票、结果或归档阶段只可给已有正式候选补录，为已通过记录，不产生新候选或额外分数。删除为逻辑删除（deletedAt/deletedBy），退出公开展示与有效提名计数，原始行保留用于审计；投票开始后每部作品必须保留至少一条已通过提名，可同批新增后替换旧记录。结果响应读取最新有效提名人，保存的选票和结果快照不变。

旧第二届 QQ 单条同步接口保留兼容，qqSync 旧数据无需迁移。所有更改沿用 JSON 字段，无需新增数据库表或执行迁移；上线时同时更新前后端并重启 API。

## Bangumi 提名的会社补全

选择 Bangumi 的新条目时，制作组／会社可自行填写，非空自填值优先于 Bangumi 资料；留空时沿用来源资料。作品已在公开书库且会社为空时，提交提名可补全空缺，保留原添加人并更新资料版本；已有非空会社不通过再次提名覆盖，应在书库管理修改。Bangumi 原始快照保留，提名失败时补全随事务回滚。

## 超级管理员编辑已提名作品

候选卡片上的“编辑作品”入口仅对超级管理员开放，可修改名称、原名／副标题、会社和简介，并使用现有封面组件上传或更换封面。名称、会社更新当前届次该作品的全部提名；其他资料更新书库。窗口提供直达“管理本作提名人和提名词”的入口，按届次与候选编号定位。

接口 PATCH /api/admin/award-campaigns/:id/candidates/:candidateId 在事务内重新校验超级管理员身份、当前活动与作品归属，以及书库 version。相同名称已对应其他作品时拒绝，不能藉修改名称合并候选。原作品编号、候选编号、审核状态与选票关联保留；历史结果响应可显示修正后的名称和会社，结果快照、分数和排名不改。封面沿用现有独立保存接口，文字资料需点击保存。无需数据库结构迁移，前后端应一并更新。

## 作品来源、书库关联与管理权限

作品的资料来源和提名人的来源是两类字段：提名人的来源仍为 displayOverride.source（如“QQ群”）；新提交的提名会由服务器保存 workSource，记录从书库选择、Bangumi 导入或手动填写，以及解析后的原书库编号、外部条目编号和原提交标题。后台补录提名人复用候选的书库编号。旧记录不补造未知的提交方式，界面明确以当前书库关联为准。

超级管理员可在提名卡片“编辑作品”中查看当前书库编号、原收录人、Bangumi 条目和各条原提交来源。即使作品由普通成员添加，也由超级管理员管理。资料保存携带 workId 与 version；关联已变更的旧窗口不能误改另一部作品。

作品只要有关联提名记录（包含待审核、通过、退回、撤回及保留的删除记录），资料、封面、Bangumi 同步、删除和恢复收录均要求超级管理员。普通管理员只可在后台管理未提交作品。接口在目录事务锁内校验，以拒绝旧页面或直接请求绕过；后台对已提交作品显示只读提示，作品详情页也隐藏普通账号的封面修改入口。

GET /api/admin/award-campaigns/:id/candidates/:candidateId 仅超级管理员可读取完整作品来源信息。PATCH /api/admin/award-campaigns/:id/candidates/:candidateId/work 可更正为关联已有书库作品，携带 currentWorkId、currentVersion、目标 workId 和 version。只允许筹备或提名阶段；投票开始后只能更正资料，不能更换作品身份或合并候选。

若本届已有相同书库编号的候选，关联更正会把全部提名（含历史状态）合并到该候选，不产生第二部作品。保留账号、提名词、时间、来源和审核状态，其他届次不变；整个操作在同一事务内并记录审计。原书库条目保留，避免破坏已有书单或帖子，历史重复书库条目的清理由管理者另行核对处理。多位提名人或超级管理员重复补录仍可保留，同一书库作品在本届只对应一个有效候选。

管理权限标记 submittedForAwards 动态读取已有提名关联，不由客户端提供；本次沿用既有数据表及 JSON，无需数据库迁移。部署时同步更新前后端并重启 API。

## 超管书库快捷入口与缺失关联补录

提名卡片的“编辑作品”窗口顶部提供“查看书库作品”和“编辑书库资料”。两者在新标签页打开，分别跳到 /works/:id 与 /admin/works?work=:id；后台按 work 参数自动定位该条作品，保留原窗口尚未保存的内容。

已有有效书库关联直接复用记录；旧提名缺少编号或关联的书库记录缺失时，超级管理员打开窗口会通过 POST /api/admin/award-campaigns/:id/candidates/:candidateId/library 补齐关联。服务端先按现有编号、保存的 Bangumi 编号及规范化名称／别名查找，未找到才自动创建基础书库资料。重复打开不会重复收录，原提名人、提名词、审核状态和选票保留。

筹备与提名阶段若匹配到本届已有候选，会合并提名记录；投票开始后不自动合并不同候选，缺少书库的独立候选可补齐编号并保留原候选和票数。已主动移出书库的记录不会自动恢复，应先核对后手动处理。新建或恢复操作只走带 CSRF 的写接口，GET 不写数据库；已有记录保持原版本，补录操作留审计日志。普通管理员仍只维护未提交作品。无需数据库迁移，但自动补录入口需更新并重启后端。
